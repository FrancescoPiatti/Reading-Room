# Reading Room — Gemini CLI context

A personal catalogue of focused paper breakdowns. Reports are generated **interactively** (no external assistant API or non-interactive assistant CLI) and rendered to a static site you can open locally or host on GitHub Pages.

## How it works
- `/explain-paper <arxiv-id | url | path.pdf> [--views …] [--depth …] [--audience …] [--focus "…"] [--approve]` reads a paper and writes `reports/<id>/digest.json` (structured data + per-section HTML you author). The input can be an arXiv id/URL, a direct PDF URL, or a **local PDF path** — that's how you add a paper that isn't on arXiv.
- `/compare <id> <id> [<id>] [--focus "…"] [--approve]` writes a side-by-side `compares/<slug>/compare.json`. With `--focus "<question or topic>"` the comparison is **organised around that question** — the framing, the chosen dimensions, and the verdict answer it — and it is stored as `"focus": "<text>"` in `compare.json` (**plain text, no HTML** — the build escapes it and renders it as a Question callout under the lead; omit the key when none was given); the title may reflect it. The app's Compare overlay has a **search box** over the paper checklist (title/venue/year/id substring; selected papers stay selected when filtered out) and a "Question or topic (optional)" input that becomes `--focus` (double quotes swapped for single; single line).
- `/learn <id> [topic] [--approve]` has an **interactive discussion** about a catalogued paper, then on **End chat** / "done" **compacts** it into a standalone Discussion stored like a comparison (`chats/<slug>/chat.json`) and listed **below the reading list** — it is never a paper/digest or catalogue card.
- `/deep-dive <id> <topic> [--into <section> | --append] [--approve]` authors a worked derivation / proof / mechanism trace and either **appends** it to the digest's `deepdives` array (a "Deep dive" tab) or **merges** it into a named section (asked per run).
- `/remove <id> [--approve]` deletes a paper (digest, notes, downloaded PDF, and the generated `docs/papers/<id>/` page) and rebuilds; it reports any comparisons / citations that referenced it. It is destructive, so it confirms the exact paths first unless `--approve` is given.
- `/refresh-venues` scans papers still marked as arXiv preprints, checks DBLP for a published version, and updates `venue` + `bibtex` for confident, non-CoRR matches while keeping the arXiv `source_url` (it applies them directly — no gate — relying on the conservative match test).
- `/backup export|import` packages **all on-disk user data** — `reports/` (analysed papers + notes), `compares/`, `chats/`, `user/` (profile/config/dismissals), and `papers/*.pdf` — into a single zip (`backups/reading-room-backup-<ts>.zip`), and restores it. It's a thin, safe wrapper around **`scripts/archive.py`** (pure stdlib): the generated `docs/` is excluded (rebuildable); `import` merges by default (`--replace` for an exact restore), first writes a safety snapshot to `backups/`, and refuses/skips unsafe zip entries (`..`, absolute paths, symlinks, out-of-scope files). Status/priority **stars** and collections live in browser `localStorage`, so `archive.py` alone can't see them: the app's **avatar menu → Back up → Full backup (zip)** writes them to `user/reading-state.json` before zipping so they travel inside the zip and are restored on import (see **Full backup from the app** below); the **Browser reading state only (JSON)** export/import stays as the secondary section — and the only option on the static site.
- `/setup` (replaces `/profile`) writes `user/profile.json` + `user/config.json` (who the reader is + their field/defaults) and **applies the customization directly, with minimal reader involvement** — it does **not** ask them to approve each change; the commands read the config at runtime so command-file edits are a genuine last resort (and, if ever needed, are applied without a per-edit gate and just mentioned in a single **final review** of how the setup looks). It personalizes the header and supplies defaults to the commands. The header **avatar menu** opens a **Profile** view (blurred-backdrop modal), an interactive **Setup** questionnaire, and a **Back up** dialog (export/import browser reading state as JSON); in the app you launch an AI (Claude, Codex, or Gemini) on the final Setup step, then Finish posts the answers to the loopback server (`/api/setup-intake` → `.setup-intake.json`) and auto-runs `/setup` in that already-open terminal — the page then shows a **"Setting up…" busy box (spinning gear)** instead of the terminal; when the agent finishes (`/setup` deletes the intake file → the watcher broadcasts `setup-done`), the terminal drawer **auto-closes**, the box flips to ✓, and the page reloads after the rebuild. **Re-running `/setup` over an existing non-factory setup first reads the previous config and leads its final review with a "What changed" delta** (old → new; surgical apply — custom tags/views the reader didn't change are kept; consequences like now-invalid tags are called out). First-time setup skips the comparison. `/setup` also **seeds `user/profile.md`** (the free-form full profile — only if absent) from the answers, with headings `# <name>` / `## Background` / `## What I'm working on` / `## What I want from reports`; the Profile modal's **Edit full profile** button edits it afterwards. The profile's optional `tagline` renders as the catalogue's subtitle (`{{TAGLINE}}`, default "Focused breakdowns of the papers worth keeping."). On the static site Setup degrades to a copyable profile + instructions.
- `--approve` on `/explain-paper`, `/compare`, `/learn`, `/deep-dive` skips the Gate's wait (the outline is still posted for the record, then it writes straight away); on `/remove` it skips the delete-safety confirmation.
- `/update` brings this clone up to date **safely, through its own git remote and credentials** (never the GitHub API — the repo may be private; never a zip over HTTP, never a reinstall): `git fetch`; show what's new (`git log HEAD..origin/<branch>`, `VERSION` → remote `VERSION`, `CHANGELOG.md`); protect the reader's data (`reports/`, `compares/`, `chats/`, `user/`, `papers/` are theirs — never stashed, reset, or discarded; `docs/` is generated); `git checkout -- docs`; `git pull --ff-only`, and if that fails resolve conflicts **keeping the reader's data and taking upstream for code/templates**; `npm install` in `workmode/` if `package.json` changed; read `UPGRADING.md` if present and **carry out** any migration it describes; `python3 scripts/verify.py --build`; then tell the reader to restart the app (close the window, reopen). It is the fallback the app's **Updates** modal hands off to ("Let the assistant do it") when its own fast-forward apply can't finish. Never uses an API.
- `python3 scripts/build.py` (pure stdlib, no deps; plain `python` on Windows — the server itself probes `python3`, `python`, `py`) renders every digest into `docs/papers/<id>/index.html`, rebuilds the searchable catalogue `docs/index.html`, the reference-library `docs/library.html`, the connections graph `docs/graph.html`, any comparison pages `docs/compare/<slug>/index.html`, and any discussion pages `docs/chat/<slug>/index.html`. It also copies the **self-hosted assets** into `docs/assets/`: vendored `fuse.min.js`/`d3.min.js` + the woff2 fonts from `templates/vendor/` (no Google Fonts / CDN pings; pages work offline — only MathJax stays on a pinned, SRI-checked CDN and degrades to raw LaTeX offline) and the tutorial screenshots from `assets/shots/`. `finalize_page` resolves three page-wide placeholders at the end: `{{SITE_TITLE}}` (config `site_title`, default "Reading Room"), `{{TAGLINE}}` (profile `tagline` — the catalogue subtitle), and `{{ASSET_ROOT}}` (`""` at docs root, `"../../"` for papers/compare/chat pages).
- `python3 scripts/verify.py --build` builds then runs QA (digest schema, **authored-HTML tag balance + LaTeX delimiter pairing**, **cites[].id normalization + `published` schema**, **field-pack validation**, placeholders, embedded-JSON, script balance, BibTeX, WCAG contrast). Prefer it over a bare build; the `verify-build` skill wraps it. Fix `✗` failures; `!` warnings are advisory.
- The source of truth is the digests in `reports/` (and `compares/`, `profile.json`). `docs/` is fully generated — never hand-edit it; re-run the build.
- Read PDFs with the Read tool directly (it renders pages). Don't leave extracted `.txt` next to PDFs — `papers/*.txt` and `.cache/` are gitignored.
- **The app (`workmode/`) — the default way to use Reading Room; never call it "work mode" in user-facing text** (UI strings, README, website, tutorial, command output say "Reading Room" / "the app"; the `workmode/` directory and the `RR_WORKMODE` JS globals keep their internal names). Its selling point to surface: **no API key / no API billing** — reports are written by the reader's own interactive assistant (Claude Code, Codex CLI, Gemini CLI) under their existing subscription. Double-click `ReadingRoom.app` (macOS) / `ReadingRoom.bat` (Windows) — or, as the terminal-only alternative (mentioned briefly, never showcased), `cd workmode && npm start` — to serve the same UI on `127.0.0.1` with an integrated AI terminal (Claude, Codex, or Gemini) + live rebuilds (it calls `python3 scripts/build.py`; it never reimplements the build). It is loopback-only; the static `docs/` and the GitHub Pages browse path keep working without it. Needs Node 18+ (static build still needs nothing but Python). The double-click launchers start the server headless (`ReadingRoom.app` opens no Terminal window at all and reports errors via a dialog; `ReadingRoom.bat` is the Windows launcher — logs go to `workmode/workmode.log`, pid to `workmode/workmode.pid`; closing the app window auto-quits the server); `npm start` instead runs it in the foreground with visible logs. **The .app must NOT detach the server** (`nohup …&` + exit): the server runs as the launcher's child with the launcher `wait`ing (LSUIElement keeps it out of the Dock) — a detached child dies when the app process exits. The .app also pre-flights **file access** (repo in a TCC-protected place — OneDrive/iCloud/Desktop/Documents — can be silently unreadable to the app even when Terminal reads it fine; cloud-evicted "dataless" files additionally hang `require()` at server start) and shows a grant-access dialog instead of failing silently. Both launchers make a one-shot first-run **shortcut offer** (marker: `user/.desktop-shortcut-offered`): macOS is a 3-button dialog **Not now / Applications folder / Desktop** (default Desktop; Applications = a `Reading Room.app` symlink in `/Applications` if writable, else `~/Applications`, `mkdir -p`); Windows: **Yes = Desktop, No = Start Menu (Programs), Cancel = skip** (a `.lnk` with `assets/ReadingRoom.ico`). Both launchers run the server **in a loop that relaunches it when it exits with code 75** ("restart me", used by in-app updates; any other exit code ends the loop) — on Windows that loop is `workmode/run-server.cmd`, which `ReadingRoom.bat` starts hidden via `Start-Process`; `npm start` users simply rerun. **First launch of a fresh clone runs `npm install` (1–3 min) with the .app showing nothing** — so the launcher posts a notification up front ("first-run setup, the window opens when ready"), holds `workmode/.install.lock` so an impatient second double-click can't race the install, and rebuilds `node-pty` explicitly if npm's script policy skipped its native build (otherwise the app opens with the terminal dead). The server falls back to the next port if one is busy (so a stale instance won't block a fresh launch). The launcher leads with **GUI flows** (app-first) rather than pre-typed commands: an **Analyze paper** button (primary) plus a **▾ flow split** (Compare · Discuss · Deep dive), each opening a full-screen overlay that shares one boot-wait/job runner. **Analyze / Compare / Deep dive run HIDDEN**: they collect inputs in the overlay (a paper picker reads `/api/reports`; Deep dive's section dropdown + before/after snapshot read `/api/digest`), launch the chosen assistant (claude/codex/gemini, persisted `rr-wm-ai`) in the **hidden** shared pty, and send the `/…  --approve` command once it's booted (marker-based wait: fires once the TUI takes over the screen — alternate-screen switch `ESC[?1049h` or a redraw burst — plus a short settle, hard-capped; quiet-detection is WRONG here: it fires into the silent gap while the assistant's process loads, and the tty then delivers text+Enters to the TUI as one pasted read, leaving the command unsubmitted) — no terminal to look at. The command is submitted **two-phase** (text first, then Enter separately, twice — `typeCommand`): text+Enter in one chunk reads as a *paste* to the TUIs and the Enter gets swallowed, leaving the command sitting in the composer unsubmitted. The same two-phase send backs End chat and Setup's auto-run `/setup`. Completion is **filesystem-detected** — the watcher broadcasts `report-added` (new `reports/<id>/digest.json` → Analyze → **Open report**), `compare-added` (new `compares/<slug>/compare.json` → Compare → **Open comparison**), or `report-changed` (an existing digest changed → Deep dive; deep-dive edits in place, so "done" is a **content diff** — deepdives grew, or the merged section's html changed); the client then polls until the page/section is built. A **quiet watchdog** (90 s of pty silence mid-job) flips the overlay status to "the assistant may be waiting for you" and toasts a **Show terminal** action when the overlay is closed — purely advisory: the job is never auto-killed and the warning retracts when output resumes. **Discuss is interactive by design**, so it opens the **visible** terminal running `/learn <id> <topic> --approve`; on **End chat** the watcher's `chat-added` offers to open the saved Discussion. A **Show terminal** button on the hidden flows reveals the same live session (for the assistant's own permission prompts). This is a UX veneer over the interactive CLI — it never uses a provider API / non-interactive mode (e.g. `claude -p`) (the interactive CLI is the only sanctioned path to the reader's own subscription); to pre-type a raw command instead, open the Terminal and type it. The Terminal split button (main = toggle the drawer) has a ▾ that launches an AI — `claude` · `codex` · `gemini` — in the shell. **Assistants always launch in AUTO mode** (client `AI_CMD` map: `claude --permission-mode bypassPermissions` · `codex --dangerously-bypass-approvals-and-sandbox` · `gemini --yolo`) — the hidden flows fire `/… --approve` commands unattended, and a permission prompt mid-run would stall the job with nothing on screen. The server **augments PATH at startup** with the standard install dirs (`~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.npm-global/bin`; npm dir on Windows) because a double-clicked .app inherits launchd's minimal PATH — without this, installed assistants get greyed out in the pickers and `which()` misses them. The terminal drawer has an **End chat** button (shown once you start a Discussion) that sends the "done" signal to a running `/learn` discussion so it compacts and writes the chat. The AI launch buttons clear the input line first (Ctrl+U), so switching assistants never leaves leftover pre-typed text to delete by hand. The terminal drawer **never opens itself** — not on page load, not on navigation (an auto-reappearing drawer reads as a bug); it opens only on explicit action: the Terminal button, starting a Discussion, a "Show terminal" escape hatch, or End chat. A **discussion page** gets a **Remove discussion** button that calls `/api/remove-chat` to delete `chats/<slug>/` + its generated page and rebuild. Ghost-node and reading-queue Analyze/Dismiss/Keep actions live in `templates/graph_addon.html` (injected into `docs/graph.html` by the build); **Analyze opens the Analyze overlay with the id already in the bar** (`RR_openAnalyze`; `RR_openDiscuss` is the analogous hook) — never the terminal; dismissals persist to `dismissed.json`, which the build honors (ghosts have no *View PDF* — they aren't downloaded). Report pages get a *View PDF* button that opens the analyzed paper inside the app via the server's `/pdf` route (serves the local `papers/<id>.pdf` or proxies arXiv same-origin so it can be framed), and an **Edit notes** button — a full-screen editor for `reports/<id>/notes.md` backed by `GET/POST /api/notes` (id shape-validated against `reports/`; empty save deletes the file; save rebuilds + reloads). External links open in the system browser via `/api/open`. **Launching an AI always respawns the shared pty** (`respawn` ws message, epoch-guarded server-side) so `codex` is never typed into a running `claude`; the tutorial seen-flag is per-INSTALL: under the app the key is `rr-tutorial-seen@wm:<install-id>` where the id is a random value persisted in `user/.install-id` on first server start (gitignored — so delete + re-clone into the SAME folder still counts as a fresh copy; a path hash did not); on file:///Pages it falls back to `rr-tutorial-seen@<site-root-path>`.
- **Jobs — stop from the app + detect the assistant exiting** (ws messages on `/__workmode/ws`). Client → server: `{type:'job-start', kind:'analyze'|'compare'|'deepdive'|'discuss', id?}` right after the flow command is submitted (`runJob` sends it from `armSend`'s `onSent`; Discuss sends it once its `/learn` command is armed) — the server takes a **snapshot** (the `reports/<id>` dirs with a `digest.json`, `compares/<slug>` with `compare.json`, `chats/<slug>` with `chat.json`, `papers/*.pdf` names, and for `deepdive` the exact bytes of `reports/<id>/digest.json`), stores `activeJob = {kind,id,snapshot,startedAt}`, and polls every 2 s whether the pty shell (`sharedTerm.pid`) still has child processes (darwin/linux `pgrep -P <pid>`; win32 a `Get-CimInstance Win32_Process -Filter 'ParentProcessId=<pid>'` count). After **3 consecutive polls with zero children** it broadcasts `{type:'agent-exited'}` once and stops polling (keeping `activeJob` so a stop can still roll back). `{type:'job-end'}` = the client verified the result → clear `activeJob` + polling (`jobDone` sends it; for Discuss the `chat-added` broadcast does). `{type:'job-stop', reason:'user'|'exited'}` → for `'user'` the server kills the pty (`killTerm()`, `termBuffer=''`, broadcast `{type:'exit'}` like a normal exit) so the assistant dies; then **rollback against the snapshot**: delete `reports/<id>`, `compares/<slug>`, `chats/<slug>` dirs that exist now but weren't in the snapshot (and their generated `docs/papers|compare|chat/…` pages), delete `papers/*.pdf` not in the snapshot, and for `deepdive` restore `reports/<id>/digest.json` from the snapshot bytes if it now differs; `runBuild` if anything changed; reply `{type:'job-stopped', removed:[relative paths], restored:boolean}` to the requesting socket; clear `activeJob`. **Never delete anything that was in the snapshot.** Client: the running overlay has a red/ghost **Stop** button → confirm row "Stop and discard? Nothing will be added to your library. [Stop] [Keep running]" → cancels arm/poll/watchdog, sends `job-stop` `'user'`, shows "Stopping…", and on `job-stopped` a final "Stopped — nothing was added to your library." with **Close** / **Try again** (reopens the same flow's form); `{type:'agent-exited'}` while a job is active and not done → `job-stop` `'exited'` + "The assistant was stopped before finishing (from the terminal). Nothing was added to your library." (this is what fixes the overlay spinning forever after a terminal Ctrl-C; the old pty-`exit` path does the same rollback). Discuss shows a **Stop discussion** (ghost/danger) button next to End chat while `/learn` runs — `job-stop` `'user'`, nothing saved, both buttons hide. **Ownership + safety (1.1.0 review fixes):** `job-start` is answered with `{type:'job-started', kind, id, token}`; `job-end` / `job-stop` must carry that `token` or they are ignored (`job-stopped … stale:true`) — except a token-less `job-stop 'user'`, which is **kill only** (a Stop before the run was registered: the booting assistant dies, nothing is rolled back). The server also **completes the run itself** when the watcher sees its artifact land (`report-added` / `compare-added` / `chat-added`, or `report-changed` for the registered id), so a page that navigated away can never roll finished work back; `/api/status.job` carries the token and a freshly loaded page **adopts** a still-running job (`adoptJob`: completion toast with Open, the flow buttons show its card with Stop, Discuss re-shows End chat / Stop discussion). A `respawn` while a run is registered stops it properly first (kill + rollback + `job-stopped`), and the client's `abandonRuns()` does the same before any manual AI launch (Terminal ▾, Setup, "Let the assistant do it"). Rollback is **scoped by kind**: analyze → new `reports/` dirs + `papers/*.pdf`, limited to the run's own id when known (re-analysing a catalogued id registers that id and restores its old digest on Stop, and "done" also accepts `report-changed` for it); compare → `compares/`; discuss → `chats/`; deepdive → digest restore only. The child-process poll reports *unknown* (never a strike) when the pty process is a tmux/screen/zellij client, and `killTermForJob` only broadcasts its `exit` if no newer shell exists (epoch guard); on the client, an `exit` that arrives while a (re)spawn handshake is in flight (`awaitingReady`) is ignored — it is the old shell's, and resetting the handshake there dropped a queued "Launch codex" right after a Stop.
- **Full profile** (`user/profile.md`): free-form Markdown about the reader — background, current projects, what they want from reports, style preferences. Optional; `/explain-paper`, `/compare`, `/learn`, `/deep-dive` read it when present and calibrate to it (in addition to `profile.json`). `/setup` **seeds it only if absent** from the answers, with headings `# <name>` / `## Background` / `## What I'm working on` / `## What I want from reports`. App routes: `GET /api/profile-md` → `{ok, text, exists}`; `POST /api/profile-md {text}` → `{ok}` (empty/whitespace text deletes the file; creates `user/` if missing; no rebuild). `window.RR_editProfile()` (in `workmode.js`) opens a full-screen Markdown editor like Edit notes; the Profile modal (`templates/account.html`) gets an **Edit full profile** footer button + a "Full profile" excerpt (first ~400 chars, escaped, pre-wrap — or "No full profile yet — write one so reports fit you better.") only when `window.RR_WORKMODE` is set. The editor's **Save & review** saves, then launches the chosen AI visibly and arms **`/setup --review-profile`**: `profile.md` is the source of truth, the command reconciles `profile.json`/`config.json` with it surgically (never rewrites the Markdown) and ends with the "What changed" review.
- **Per-assistant command form** (`flowCommand()` in `workmode/client/workmode.js`): Claude and Gemini receive the slash form (`/explain-paper …`); **Codex rejects unknown slash commands client-side**, so it receives the skill mention `$explain-paper …` (its skills live in `.agents/skills/<name>/`). Codex is launched with `-c check_for_update_on_startup=false`. The built pages' authored HTML is sanitized by `build.py` (`sanitize_fragment`) and `verify.py` fails on active content; orphan `docs/` pages are pruned on every build.
- **Launch judging — the boot watcher** (`makeBootWatch()` in `workmode.js`, 1.3.1; replaces the byte/alt-screen heuristics and the per-install "seen" flag). Every launch (`launchAgent(name, {headless, raise, cmd, onSent, onNeedsYou, onReady, onFail})`) is judged by the TEXT of its first screens, whitespace removed and lower-cased (TUIs place words with cursor moves): a **dialog signature** (`DIALOG_RE`: claude's "Quick safety check … Yes, I trust this folder", the bypass-permissions acceptance, "Select login method"; codex's "Do you trust the contents of this directory … Press enter to continue", "Sign in with ChatGPT"; gemini's "Do you trust the files in this folder … Trust folder (…)", "How would you like to authenticate"; generic "press enter to continue" / "enter to confirm") puts the launch in **needs-you** (`reason` trust | login | confirm): the drawer is **raised above every overlay and modal** (`body.rr-term-front`, drawer z 10090; the covered panel keeps room above it), opened and focused, the drawer bar shows why, the run card / Setup box explain what to answer, and readiness then counts only on output printed **after** the dialog; a **ready signature** (`READY_RE[name]`: claude "bypass permissions on (shift…", "? for shortcuts", "❯ Try …" or the alternate-screen switch — which claude enters only after trust; codex "OpenAI Codex (v…", "permissions:", "/model to change" — codex never uses the alternate screen; gemini "Type your message", "? for shortcuts") settled `BOOT_SETTLE_MS` → `typeCommand(cmd)` + `onSent`; neither for `BOOT_CAP_MS` → needs-you **unknown**, the only state that shows **Continue** (drawer bar + run card, derived from `job.needsYou` so any re-render keeps it); Enter typed in the terminal on a recognised dialog with nothing recognised following for 2.5 s also drops to unknown. Nothing is ever typed blind: the real dialogs never trip the old heuristics (claude's trust screen is ~1.2 KB and not on the alternate screen; typing into it selected "No, exit"). "command not found" → `onFail('missing')` (the run stops with that reason); while it waits on the reader the watcher polls `GET /api/term-children` (the server's `countShellChildren`) every 3 s, and two empty polls → `onFail('exited')` — the assistant left ("No, exit", a crash) and the run says so instead of the next keystrokes landing in a bare shell. Server side, a registered run whose assistant died with **no page connected** is rolled back after 30 s (`scheduleDeadRunCleanup`, re-armed when the last page leaves); `/api/status.job.exited` lets a page that opens later end it with the truth (`adoptJob` → `stopJob('exited', …)`), and a stop sent by such a page waits for its socket (`whenTermReady`). `RR_submitCommand` (Setup's Apply) sends only when ready or unknown, never into a recognised dialog; `RR_agentState()` → `{name, live, needsYou}`; `rr-agent-state` window events (`starting | needs-you | ready | sent | gone`) drive Setup's status box. Esc / Tab with focus inside the terminal (`termHasFocus()`, `window.RR_terminalHasFocus`) never close a panel, the drawer, or a modal.
- **Setup's launch keeps the modal** (1.3.1): *Launch claude/codex/gemini* → `RR_launchAgent(name)` (refuses, with a toast, while a started run or discussion exists) → visible launch with the drawer raised **over** the Setup modal (capped to 36 vh there) — the modal stays open, its status box (top of the last step) follows `rr-agent-state`, **Apply setup** (the Finish button, in the launch row) runs `/setup` via `RR_submitCommand` and closes the drawer for the busy box; a stray click on the backdrop while the terminal is up does not close Setup; reopening Setup part-way (or after a launch) resumes at the same step; Esc in a field only blurs it; the busy box has **Close** and a "still going" note after 2 min. The old floating "Apply setup" bar is gone.
- **Assistant settings** (`workmode/client/workmode.js`): per-assistant **model** + **reasoning effort**, persisted in `localStorage` `rr-wm-ai-cfg` = `{claude:{model,effort}, codex:{model,effort}, gemini:{model}}`; `aiCommand(name)` builds the launch line = the AUTO-mode flags in `AI_CMD` + `claude --model X --effort Y` / `codex -m X -c model_reasoning_effort="Y"` / `gemini -m X` (model sanitized to `[A-Za-z0-9._:/-]`, effort from a fixed list per CLI). UI: a **Settings** gear next to the assistant pills in every flow form (inline panel + a one-line summary "claude · opus · high effort") and Terminal ▾ → **Assistant settings…** (a modal built with the account-modal classes; `window.RR_openAssistantSettings`). `launchAgent` always uses `aiCommand`, so the flow buttons, Setup's launch and the manual ▾ launches all honour it.
- **Full backup from the app** (`templates/account.html` Back up modal, app-only section "Full backup (zip)"; the "Browser reading state only (JSON)" export/import stays as the secondary section and is the only option on the static site). `GET /api/backup/info` → `{ok, counts:{reports,comparisons,discussions,pdfs}, downloadsDir|null, backupsDir}`. `POST /api/backup/export {pdfs, dest:'downloads'|'backups'|'custom', path?, state?}` — when `state` is an object the server first writes **`user/reading-state.json`** = `{tool:'reading-room', kind:'reading-state', exported:'YYYY-MM-DD', state}` so the browser reading state travels inside the zip (`archive.py` already includes `user/*`); `downloads` → `~/Downloads/reading-room-backup-<YYYYMMDD-HHMMSS>.zip` (falls back to `backups/`), `backups` → `<repo>/backups/…`, `custom` → an absolute `.zip` path (an existing directory gets the default filename; parent must exist); runs `<python> scripts/archive.py export -o <out> [--no-pdfs]` (cwd repo, 10 min timeout) → `{ok, path, counts, includes_pdfs, bytes}`. `POST /api/backup/reveal {path}` reveals it in Finder/Explorer (`open -R` / `explorer /select,` / `xdg-open dirname`) — only paths this server process exported are accepted (a Set), else 400. `POST /api/backup/import?mode=merge|replace` takes the **raw zip bytes** (streamed to disk, 8 GB cap) → writes `backups/import-<ts>.zip`, runs `scripts/archive.py import <zip> [--replace]` (which makes its own pre-import snapshot), reads `user/reading-state.json`'s `state` if present, `runBuild`s, then responds `{ok, written, manifest, state|null}` (after the build, so the client can reload); the client writes every returned key that passes `isStateKey` into `localStorage`, then reloads. Errors → `{ok:false, error}` with archive.py's stderr tail. The upload is **streamed** to `backups/import-<ts>.zip` (never buffered in RAM; 8 GB cap, PK magic checked on the first chunk) and `state` comes back **only when that zip actually contained `user/reading-state.json`** (a stale file left by an earlier export never overwrites the browser's current stars). `scripts/archive.py` skips — and on `--replace` preserves — the per-install markers `user/.install-id` / `.desktop-shortcut-offered`, writes `<out>.zip.part` and renames on success, and stops with a clear message on an unreadable (cloud-evicted) file; a custom export path that already exists is refused (400).
- **Updates** (git-based; the repo may be private, so it uses the clone's **own git credentials — never the GitHub API**). Repo-root **`VERSION`** (semver), **`CHANGELOG.md`** (newest first, `## 1.1.0 — 2026-09-12` sections), optional **`UPGRADING.md`** (maintainer notes for updates that need the assistant's help). `GET /api/update[?refresh=1]` → `{ok, git, checked, available, behind, ahead, branch, local:{commit,version}, remote:{commit,version}, changes:[{sha,subject}] (newest first, max 30), upgradingChanged, error}` — the server checks 5 s after listening and every 6 h (and on `refresh=1`): `git fetch --quiet origin` (spawn, `GIT_TERMINAL_PROMPT=0`, 30 s timeout); branch = `git rev-parse --abbrev-ref HEAD` (detached → `main`); `behind`/`ahead` = `git rev-list --count` each way against `origin/<branch>`; `changes` = `git log --format=%h%x09%s HEAD..origin/<branch>`; versions = local `VERSION` and `git show origin/<branch>:VERSION`; `upgradingChanged` = `git diff --name-only HEAD..origin/<branch>` includes `UPGRADING.md`; not a checkout / no origin / fetch failed → `git:false` or `error`, `available:false`; result cached. `POST /api/update/apply` (progress via ws `{type:'update-progress', step:'pull'|'install'|'build', msg}`): (1) `git checkout -- docs` if docs/ has tracked modifications (generated, rebuildable); (2) `git pull --ff-only origin <branch>` — failure → `{ok:false, stage:'pull', error, needsAssistant:true}`; (3) `npm install --no-audit --no-fund` in `workmode/` if `package.json`/`package-lock.json` changed (5 min); (4) `runBuild` → `{ok, from, to, restartNeeded (any file under workmode/ changed), upgradingChanged}`. `POST /api/update/restart` broadcasts `{type:'restarting'}` then `process.exit(75)` (~300 ms later) — the launchers' loop relaunches on 75; `GET /api/status` carries `startedAt` (ISO) so the client can tell the new server from the old. Client: on load fetch `/api/update`; if `available` && `the update id is neither skipped nor deferred (see below)` && the tutorial has been seen && no `.rr-modal` is open → after 1200 ms open an **Update available** modal built with the account-modal classes (`.rr-modal` > `.rr-modal-backdrop` + `.rr-modal-card[role=dialog]` > head/body/foot; `.rr-btn` / `.rr-btn-ghost` / `.rr-btn-go`; `rr-modal-open` on body): "Reading Room <remote.version> is available — you have <local.version>" (fallback "<behind> new change(s)"), the change list, "Your library, notes and settings are never touched by an update."; **Later** / **Skip this version** store `rr-update-later` / `rr-update-skipped` (see below); **Update now** shows a step list driven by the broadcasts, then "Installed. Restart Reading Room to finish." + **Restart now** (POST restart, poll `/api/status` every 1 s up to 90 s until `startedAt` differs, `location.reload()`); failure → error text + **Let the assistant do it** (opens the terminal drawer, launches the chosen AI visibly and arms `/update` like Discuss) + **Close**. `window.RR_openUpdates(force)` fetches with `refresh=1` and opens the modal (or "You're up to date (1.1.0)"); the avatar menu gets an **Updates** item (inserted at DOMContentLoaded only under `RR_WORKMODE`). `/api/status` also carries `restartable` (`RR_LAUNCHER=1`, exported by ReadingRoom.app's loop and `workmode/run-server.cmd`) and `restartPending` (an applied update touched `workmode/` and the server hasn't restarted); without a launcher loop `POST /api/update/restart` answers 409 and the installed state tells the reader to stop/start the server by hand; a page load with `restartPending` toasts a **Restart now** reminder; the version headline is used only when the remote `VERSION` differs. A server relaunched with `RR_NO_OPEN=1` (no `RR_KEEPALIVE`) quits after 30 s if no window connects (orphan guard). `run-server.cmd` keeps its loop in one parenthesised block so an update that rewrites the file can't derail cmd.exe mid-line. The loopback **Host** check now applies to every HTTP method, so a DNS-rebinding page can't read `/api/profile-md`, notes or the repo path. **ZIP installs** (no `.git`): `doUpdateCheck` fetches the published `VERSION` (and `CHANGELOG.md` for the change list — bullets of every section newer than the local version) from `raw.githubusercontent.com/<UPDATE_REPO>/<UPDATE_BRANCH>/` (`RR_UPDATE_REPO`/`RR_UPDATE_BRANCH`; `RR_UPDATE_BASE` is a test hook serving `VERSION`, `CHANGELOG.md`, `release.zip`), reports `method:'zip'`, and `apply` downloads the branch archive to `backups/update-<ts>.zip` and runs **`scripts/update_zip.py`** (stdlib; overlays every app file in place, never writes `reports/ compares/ chats/ user/ papers/ backups/ workmode/node_modules/`, prints `{changed, added, restartNeeded, installNeeded, upgradingChanged}`), then npm-installs if `workmode/package*.json` changed and rebuilds. Dismissals are keyed on `updId = remote.version || remote.commit`: **Later** stores `rr-update-later {id, startedAt}` (suppressed only while the same server instance runs), **Skip this version** stores `rr-update-skipped = id` (never again for that id; a newer id is offered). **The channel is the published RELEASE, not the branch head** (1.3.0): `latestRelease()` reads `https://api.github.com/repos/<UPDATE_REPO>/releases/latest` (override `RR_UPDATE_API`; skipped when `RR_UPDATE_BASE` is set), takes `tag_name` → `remote.version`, prefers the asset whose name matches this platform (`mac|darwin` / `win` / `linux`, `.zip`) and otherwise the tag archive, and reads the CHANGELOG at that tag; the result carries `channel:'release'|'branch'`, `tag`, `packaged`, `zipUrl`, and `apply` downloads `info.zipUrl`. No releases published (or the API unreachable) → it falls back to the old raw-branch behaviour, so copies installed before 1.3.0 keep working. The git path now fetches `--tags` too and names the newest `v*` tag. **Every apply first writes a PDF-less snapshot** `backups/pre-update-<ts>.zip` (`snapshot()`; the newest 5 of each prefix are kept) and reports it as `backup` / `backupError`. **`main` is the release branch** — cut development elsewhere and merge on release, because a ZIP copy updating from the branch head would otherwise land mid-work code.
- **Reading state on disk** (1.3.0). Status / priority / collections / ghost dismissals / theme live in `localStorage`, which the browser scopes to the **origin — port included**, so the port fallback (4317 busy) or another browser made the library look unread. Under the app **`user/reading-state.json` is the source of truth**: `injectWorkmode` also splices a `<script>` into `<head>` (`stateSnippet()`) that sets `window.RR_STATE` and writes every key into `localStorage` **before the page's own scripts parse** (seeding after `</body>` is one paint too late — the theme guard and the catalogue read it during parse); the client wraps `localStorage.setItem`/`removeItem` and POSTs changes (debounced 250 ms, `keepalive` on `pagehide`) to `POST /api/reading-state {set:{},remove:[]}`, filtered by the same key whitelist the backup uses (`isStateKey`). `GET /api/reading-state` → `{ok,state}`. It is the same file the backup zip carries, so a restore lands here. The static site is unchanged (browser only) — that is what the JSON export is for.
- **Analyze takes PDFs from disk, a stack at a time** (1.3.0). `POST /api/paper-upload?name=<filename>` streams the raw body to `papers/<slug>.pdf` (`%PDF-` magic checked on the first chunk, 200 MB cap, slug sanitised so a `../` name can't escape `papers/`, `-2`/`-3` suffixes rather than overwriting) → `{ok,id,path}`; the Analyze panel has **Choose PDF…** plus drag-and-drop on the whole card and then analyzes `papers/<slug>.pdf`. **Add another** builds a queue (chips with a remove ×); one run at a time — `startAnalyzeQueue` → `queueNext()` starts the next only after the previous one lands, because the server registers a single `activeJob` whose rollback is scoped to one artifact. A spec may carry `onDone(id)` (return `true` to suppress the single-paper done card — the queue renders its own progress and a final list) and `onStopped()` (a stopped queue stops for good). Per-run **Options** (depth / audience / focus) become flags on the command, and a flag the reader typed by hand always wins.
- **Remove paper + Diagnostics** (1.3.0). `POST /api/remove-paper {id}` answers with the **plan** (`paths` that exist: `reports/<id>`, `papers/<id>.pdf`, `.cache/<id>.txt`, `docs/papers/<id>`, plus `compares`/`citedBy` dependents); with `{confirm:true, compares?:true}` it deletes exactly those and rebuilds — the same set `/remove` documents, dependents reported and never deleted unasked. `GET /api/diagnostics` → versions (node/npm/python/each assistant, 8 s probes), install method (git → commit/branch/tag, else zip), port, repo, uptime, library counts and the last 60 lines of `workmode/workmode.log`; the avatar menu's **Diagnostics** item opens it with a **Copy** button.
- **A run outlives its window** (1.3.0). `maybeShutdown()` and the `RR_NO_OPEN` orphan guard both re-arm instead of exiting while `activeJob` is set, so closing the app mid-analyze no longer kills the assistant and loses the report — the server waits, the watcher completes the job, docs rebuild, then it quits. The run card shows elapsed time and the assistant's **last readable line** (`noteOutput` strips CSI/OSC and box drawing; advisory only).
- **Backups on a schedule** (1.3.0). `user/app-prefs.json` `{autoBackupDays: 0|1|7|30}` via `GET/POST /api/backup/prefs`; on start + every 6 h `maybeAutoBackup()` writes `backups/auto-<ts>.zip` (no PDFs) when the newest zip is older than that, never mid-update or mid-run. The Back up modal's app-only section carries the control.
- **Linux + packaged releases** (1.3.0). `ReadingRoom.sh` is the third launcher (same invariants: server as a child, exit-75 restart loop, `RR_LAUNCHER=1`; first run offers a `~/.local/share/applications` entry; `notify-send` when there is no console). `scripts/package_release.sh` builds `dist/ReadingRoom-<version>-<os>-<arch>.zip` = `git archive HEAD` + a production `npm install` (so no first-launch install and no native build for the reader) + the CHANGELOG section as release notes; the zip has one top-level folder, which is what `update_zip.py` expects. `dist/` is gitignored.
- **Catalogue/Library sort + a11y** (1.3.0). Both pages have a Sort select (year · recently updated · title · priority · status; remembered as `rr-sort`), fed by a new `updated` stamp (the digest's mtime) that `build.py` puts in `catalogue.json`/`library.json`; the Library filter also searches id, year and `tldr`. The app's full-screen panels are dialogs — one `MutationObserver` on `.rr-analyze-overlay, .rr-pdf-overlay, .rr-notes-overlay` sets `role="dialog"`/`aria-modal`/`aria-label`, moves focus in, traps Tab, restores focus on close, and Esc closes the flow/diagnostics panels; run status is `role="status" aria-live="polite"`; graph nodes carry `tabindex`/`role="link"`/`aria-label` with Enter/Space and focus-highlighting; the terminal has an optional **screen-reader mode** (`rr-wm-sr`, Assistant settings) and an `aria-label`ed region.

## Conventions
- Always pause at the command's **Gate** (outline / dimensions) before writing a digest or comparison — **unless `--approve` is passed** (still post the outline for the record, then write). `/refresh-venues` no longer gates (it applies only confident matches); `/remove` confirms the delete instead (skippable with `--approve`).
- Keep claims grounded; cite section/figure numbers; never invent metrics.
- To add a focus view, add it to `user/config.json` `sections` (or a `templates/fields/*.json` pack) and to the command's section list — it renders automatically wherever a digest provides it. **Don't edit `SECTION_ORDER` in `scripts/build.py`** — that's a fallback used only when no config declares sections, so edits there have no effect once a config exists. (Custom one-off sections — e.g. from `--focus` — render even without being listed.)
- **Field config & maintenance safety**: user-specific config (`profile.json`, `dismissed.json`, `config.json`) lives under **`user/`** (gitignored) so app updates never overwrite it; `scripts/build.py`'s `user_path()` resolves `user/<name>` → legacy repo-root `<name>` → shipped `*.example.json`, so an un-migrated repo still works. **Discipline is a config choice**: `user/config.json` names `fields` (e.g. `["ml"]`, `["bio"]`, `["econ-finance"]`) which merge the shipped `templates/fields/*.json` packs (tag vocabulary + focus-view titles + lens + tone), and may carry an explicit `tags`/`sections` override **alongside** `fields` — `merge_field_packs` is **base-wins**, so it keeps your explicit values and fills only what you omit (lens/tone) from the pack. **Merge order matters**: tags union in the order `fields` lists the packs, and each section key takes its title from the *first* pack that declares it, so `["bio","ml"]` ≠ `["ml","bio"]` — the primary field goes first. Packs are schema-checked at load (`PACK_KEYS`); a typo'd key warns instead of silently no-oping. `config.site_title` renames the whole site (header/titles/credit) without code edits. The shipped `ml` pack ships a **general, math-derived** default vocabulary; a reader's own specific vocabulary lives in their `user/config.json` `tags` (Setup can add custom focus views to `sections` too). The commands and `scripts/verify.py` read this at runtime — **do not hardcode ML**. `SECTION_ORDER`/`TAG_VOCABULARY`/`MAX_TAGS`/`REQUIRED_SECTIONS` in `scripts/build.py` are now defaults/fallbacks; the live values come from `load_config()` via `section_order()`/`tag_vocabulary()`/etc.
- **Never rename a section *key*** (`summary`/`math`/`architecture`/`results`/`significance`/`reproducibility`) — all existing digests use them as storage keys. Fields only change the *titles* (a pack titles `math` "Methods & statistics" for bio, etc.). Renaming a key blanks that tab on every existing report.
- **Citations**: digests carry `cites: [{id, title}]` (normalized arXiv ids). The graph links papers and surfaces a reading queue — ghost nodes / queue entries are references cited by at least `QUEUE_MIN` (= 2, `scripts/build.py`) analysed papers; edges resolve automatically as papers are added.
- **Tags**: a controlled vocabulary, broad (2–4 per paper), never paper-specific; `scripts/verify.py` fails on any tag outside the **active** set. The active set is `config.tags` (from the user's field pack(s) or override), with `scripts/build.py`'s `TAG_VOCABULARY` as the ML default. Add a category to the field config / pack deliberately rather than inventing a one-off tag.
- **`significance`** is a default, always-written section that merges novelty + critique + why-it-matters-for-the-field. `summary` + `significance` are required (build warns if missing). **`reproducibility` is opt-in**: `/explain-paper` writes it only when explicitly requested (`--views`/`--focus`) or when the reader's setup config includes it as a default view — never by default.
- **Deep dives**: a digest may carry a top-level `deepdives` array (`{title, added (ISO date), html}`); the build renders them under one "Deep dive" focus tab. Added incrementally by `/deep-dive` (append mode); `/deep-dive --into <key>` instead merges the worked content into an existing section's `html`. Not written by `/explain-paper`.
- **Discussions**: `/learn` compacts an interactive chat into a standalone `chats/<slug>/chat.json` (`{id, title, papers, added, tldr, html}`) — stored and surfaced **like a comparison**: its own `docs/chat/<slug>/` page, a "Discussions" list below the reading list, and a "Discussed in" backlink on each referenced report. It is **never** a digest or catalogue card. Same HTML/LaTeX/grounding rules as a digest section.
- **Reading state**: `status` (`to-read`/`reading`/`read`) + `priority` (0–3 stars) are seed values; the reader edits them in the UI (report page + Library page) and choices persist in `localStorage`, overriding the digest. New papers seed `to-read`/`0`. Per-paper prose lives in `reports/<id>/notes.md`. All browser reading state lives under `rr-*` keys (`rr-status-<id>`, `rr-prio-<id>`, `rr-tags-<id>`, `rr-dismissed`, `rr-theme`) — the avatar menu's **Back up** export/import and `isStateKey` cover exactly this set, and the app's full backup zip carries it via `user/reading-state.json`.
- **Custom tags / collections** (reference-manager-style): free-form, reader-owned labels (a project name, "to-cite", …), **distinct from the controlled `tags` vocabulary**. Stored per paper in `localStorage` (`rr-tags-<id>`, a JSON array), edited on the report page (a "Collections" chip editor) and the Library. On the **Library** they render as a collections filter bar + per-row chips + a "Tag selected papers" bulk action; filtering to a collection scopes the BibTeX **Copy/Download** to that set (the `.bib` is named after the collection). Nothing in `scripts/build.py` handles them — they're a pure client/localStorage feature (like reading state), so they're never in a digest and are carried by the reading-state backup.
- **Tutorial**: a bigger stepped walkthrough (`templates/account.html`, `.rr-modal-card--wide`). It **auto-opens on first launch** (one-shot `rr-tutorial-seen`) and on close hands off to **Setup**; it's re-openable anytime from the avatar menu ("Tutorial") and is skippable/closeable. Image steps show **real screenshots** (`assets/shots/*.png`, `{{ASSET_ROOT}}`-prefixed so they resolve at any page depth); the two GIF steps show real recordings (`assets/shots/analyze.gif`, `apptour.gif`).
- **Example papers**: the template ships two example digests — `reports/1706.03762/` (*Attention Is All You Need*, the gold-standard reference for digest JSON/HTML/LaTeX conventions) and `reports/hornik1989/` (Hornik's universal-approximation theorem, a **local-PDF** example with no arXiv id) — so the first launch isn't empty, screenshots have content, and agents have a reference to follow. Their PDFs are **not** committed (`papers/*.pdf` stays gitignored); the app's View PDF proxies arXiv for `1706.03762`. Users remove them with `/remove 1706.03762` / `/remove hornik1989`.
- **Citations**: keep `source_url` on arXiv for the link, but set `published` (`{type: "article"|"inproceedings", venue, year, volume?, number?, pages?, publisher?}`) or a raw `bibtex` override so exported BibTeX is the journal/venue entry. `docs/library.html` is a grouped reference list with BibTeX export.
- **Wording**: user-facing text (UI strings, README, website, tutorial, command output) says "Reading Room" / "the app" — never "work mode" / "workmode" (the directory and `RR_WORKMODE` globals keep their internal names). The app is *the* way to use Reading Room; terminal-only usage (`cd workmode && npm start`, typing slash commands) is a one-line alternative, never showcased. Surface the selling point: **no API key / no API billing** — reports are written by the reader's own interactive assistant under their existing subscription.
- Colors live in CSS tokens — `:root` is the default **light** theme, `[data-theme="dark"]` overrides. Every page has a persisted light/dark toggle. Don't hard-code colors; add a token.

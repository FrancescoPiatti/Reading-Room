# Reading Room — context for the running assistant

A personal catalogue of focused paper breakdowns. Reports are generated **interactively** (no external assistant API or non-interactive assistant CLI) and rendered to a static site you can open locally or host on GitHub Pages.

## Native workflow invocation

- Codex-native explicit invocations are `$explain-paper`, `$compare`, `$learn`, `$deep-dive`, `$remove`, `$refresh-venues`, `$setup`, and `$backup`; pass arguments as normal text after the skill mention.
- The Reading Room work-mode UI may send the equivalent slash forms (`/explain-paper`, `/compare`, and so on). Treat each slash form as the same workflow and preserve every option, path, schema, and approval gate.
- The command-style skills are explicit-only. The reusable `$verify-build` and `$run-reading-room` skills may also trigger automatically when their descriptions match.

## How it works
- `/explain-paper <arxiv-id | url | path.pdf> [--views …] [--depth …] [--audience …] [--focus "…"] [--approve]` reads a paper and writes `reports/<id>/digest.json` (structured data + per-section HTML you author). The input can be an arXiv id/URL, a direct PDF URL, or a **local PDF path** — that's how you add a paper that isn't on arXiv.
- `/compare <id> <id> [<id>] [--approve]` writes a side-by-side `compares/<slug>/compare.json`.
- `/learn <id> [topic] [--approve]` has an **interactive discussion** about a catalogued paper, then on **End chat** / "done" **compacts** it into a standalone Discussion stored like a comparison (`chats/<slug>/chat.json`) and listed **below the reading list** — it is never a paper/digest or catalogue card.
- `/deep-dive <id> <topic> [--into <section> | --append] [--approve]` authors a worked derivation / proof / mechanism trace and either **appends** it to the digest's `deepdives` array (a "Deep dive" tab) or **merges** it into a named section (asked per run).
- `/remove <id> [--approve]` deletes a paper (digest, notes, downloaded PDF, and the generated `docs/papers/<id>/` page) and rebuilds; it reports any comparisons / citations that referenced it. It is destructive, so it confirms the exact paths first unless `--approve` is given.
- `/refresh-venues` scans papers still marked as arXiv preprints, checks DBLP for a published version, and updates `venue` + `bibtex` for confident, non-CoRR matches while keeping the arXiv `source_url` (it applies them directly — no gate — relying on the conservative match test).
- `/backup export|import` packages **all on-disk user data** — `reports/` (analysed papers + notes), `compares/`, `chats/`, `user/` (profile/config/dismissals), and `papers/*.pdf` — into a single zip (`backups/reading-room-backup-<ts>.zip`), and restores it. It's a thin, safe wrapper around **`scripts/archive.py`** (pure stdlib): the generated `docs/` is excluded (rebuildable); `import` merges by default (`--replace` for an exact restore), first writes a safety snapshot to `backups/`, and refuses/skips unsafe zip entries (`..`, absolute paths, symlinks, out-of-scope files). Status/priority **stars** live in browser `localStorage`, so they're not in the zip: export/import those from the header **avatar menu → "Back up"** (a JSON, works on the static site too).
- `/setup` (replaces `/profile`) writes `user/profile.json` + `user/config.json` (who the reader is + their field/defaults) and **applies the customization directly, with minimal reader involvement** — it does **not** ask them to approve each change; the commands read the config at runtime so command-file edits are a genuine last resort (and, if ever needed, are applied without a per-edit gate and just mentioned in a single **final review** of how the setup looks). It personalizes the header and supplies defaults to the commands. The header **avatar menu** opens a **Profile** view (blurred-backdrop modal), an interactive **Setup** questionnaire, and a **Back up** dialog (export/import browser reading state as JSON); in work mode you launch an AI (Claude, Codex, or Gemini) on the final Setup step, then Finish posts the answers to the loopback server (`/api/setup-intake` → `.setup-intake.json`) and auto-runs `/setup` in that already-open terminal — the page then shows a **"Setting up…" busy box (spinning gear)** instead of the terminal; when the agent finishes (`/setup` deletes the intake file → the watcher broadcasts `setup-done`), the terminal drawer **auto-closes**, the box flips to ✓, and the page reloads after the rebuild. **Re-running `/setup` over an existing non-factory setup first reads the previous config and leads its final review with a "What changed" delta** (old → new; surgical apply — custom tags/views the reader didn't change are kept; consequences like now-invalid tags are called out). First-time setup skips the comparison. The profile's optional `tagline` renders as the catalogue's subtitle (`{{TAGLINE}}`, default "Focused breakdowns of the papers worth keeping."). On the static site Setup degrades to a copyable profile + instructions.
- `--approve` on `/explain-paper`, `/compare`, `/learn`, `/deep-dive` skips the Gate's wait (the outline is still posted for the record, then it writes straight away); on `/remove` it skips the delete-safety confirmation.
- `python scripts/build.py` (pure stdlib, no deps) renders every digest into `docs/papers/<id>/index.html`, rebuilds the searchable catalogue `docs/index.html`, the reference-library `docs/library.html`, the connections graph `docs/graph.html`, any comparison pages `docs/compare/<slug>/index.html`, and any discussion pages `docs/chat/<slug>/index.html`. It also copies the **self-hosted assets** into `docs/assets/`: vendored `fuse.min.js`/`d3.min.js` + the woff2 fonts from `templates/vendor/` (no Google Fonts / CDN pings; pages work offline — only MathJax stays on a pinned, SRI-checked CDN and degrades to raw LaTeX offline) and the tutorial screenshots from `assets/shots/`. `finalize_page` resolves three page-wide placeholders at the end: `{{SITE_TITLE}}` (config `site_title`, default "Reading Room"), `{{TAGLINE}}` (profile `tagline` — the catalogue subtitle), and `{{ASSET_ROOT}}` (`""` at docs root, `"../../"` for papers/compare/chat pages).
- `python scripts/verify.py --build` builds then runs QA (digest schema, **authored-HTML tag balance + LaTeX delimiter pairing**, **cites[].id normalization + `published` schema**, **field-pack validation**, placeholders, embedded-JSON, script balance, BibTeX, WCAG contrast). Prefer it over a bare build; the `verify-build` skill wraps it. Fix `✗` failures; `!` warnings are advisory.
- The source of truth is the digests in `reports/` (and `compares/`, `profile.json`). `docs/` is fully generated — never hand-edit it; re-run the build.
- Read PDFs directly with the running assistant's PDF-capable file reader (it renders pages). Don't leave extracted `.txt` next to PDFs — `papers/*.txt` and `.cache/` are gitignored.
- **Work mode (optional, local).** Double-click `ReadingRoom.app` (macOS) / `ReadingRoom.bat` (Windows), or `cd workmode && npm start`, to serve the same UI on `127.0.0.1` with an integrated AI terminal (Claude, Codex, or Gemini) + live rebuilds (it calls `python scripts/build.py`; it never reimplements the build). It is **purely additive** and loopback-only: the static `docs/` and the GitHub Pages browse path are untouched. Needs Node 18+ (static build still needs nothing but Python). The double-click launchers start the server headless (`ReadingRoom.app` opens no Terminal window at all and reports errors via a dialog; `ReadingRoom.bat` is the Windows launcher — logs go to `workmode/workmode.log`, pid to `workmode/workmode.pid`; closing the app window auto-quits the server); `npm start` instead runs it in the foreground with visible logs. **The .app must NOT detach the server** (`nohup …&` + exit): the server runs as the launcher's child with the launcher `wait`ing (LSUIElement keeps it out of the Dock) — a detached child dies when the app process exits. The .app also pre-flights **file access** (repo in a TCC-protected place — OneDrive/iCloud/Desktop/Documents — can be silently unreadable to the app even when Terminal reads it fine; cloud-evicted "dataless" files additionally hang `require()` at server start) and shows a grant-access dialog instead of failing silently. Both launchers make a one-shot first-run offer to add a Desktop shortcut (marker: `user/.desktop-shortcut-offered`; macOS = symlink, Windows = `.lnk` with `assets/ReadingRoom.ico`). **First launch of a fresh clone runs `npm install` (1–3 min) with the .app showing nothing** — so the launcher posts a notification up front ("first-run setup, the window opens when ready"), holds `workmode/.install.lock` so an impatient second double-click can't race the install, and rebuilds `node-pty` explicitly if npm's script policy skipped its native build (otherwise the app opens with the terminal dead). The server falls back to the next port if one is busy (so a stale instance won't block a fresh launch). The launcher leads with **GUI flows** (app-first) rather than pre-typed commands: an **Analyze paper** button (primary) plus a **▾ flow split** (Compare · Discuss · Deep dive), each opening a full-screen overlay that shares one boot-wait/job runner. **Analyze / Compare / Deep dive run HIDDEN**: they collect inputs in the overlay (a paper picker reads `/api/reports`; Deep dive's section dropdown + before/after snapshot read `/api/digest`), launch the chosen assistant (claude/codex/gemini, persisted `rr-wm-ai`) in the **hidden** shared pty, and send the `/…  --approve` command once it's booted (marker-based wait: fires once the TUI takes over the screen — alternate-screen switch `ESC[?1049h` or a redraw burst — plus a short settle, hard-capped; quiet-detection is WRONG here: it fires into the silent gap while the assistant's process loads, and the tty then delivers text+Enters to the TUI as one pasted read, leaving the command unsubmitted) — no terminal to look at. The command is submitted **two-phase** (text first, then Enter separately, twice — `typeCommand`): text+Enter in one chunk reads as a *paste* to the TUIs and the Enter gets swallowed, leaving the command sitting in the composer unsubmitted. The same two-phase send backs End chat and Setup's auto-run `/setup`. Completion is **filesystem-detected** — the watcher broadcasts `report-added` (new `reports/<id>/digest.json` → Analyze → **Open report**), `compare-added` (new `compares/<slug>/compare.json` → Compare → **Open comparison**), or `report-changed` (an existing digest changed → Deep dive; deep-dive edits in place, so "done" is a **content diff** — deepdives grew, or the merged section's html changed); the client then polls until the page/section is built. A **quiet watchdog** (90 s of pty silence mid-job) flips the overlay status to "the assistant may be waiting for you" and toasts a **Show terminal** action when the overlay is closed — purely advisory: the job is never auto-killed and the warning retracts when output resumes. **Discuss is interactive by design**, so it opens the **visible** terminal running `/learn <id> <topic> --approve`; on **End chat** the watcher's `chat-added` offers to open the saved Discussion. A **Show terminal** button on the hidden flows reveals the same live session (for the assistant's own permission prompts). This is a UX veneer over the interactive CLI — it never uses a provider API / non-interactive mode (e.g. `claude -p`) (the interactive CLI is the only sanctioned path to the reader's own subscription); to pre-type a raw command instead, open the Terminal and type it. The Terminal split button (main = toggle the drawer) has a ▾ that launches an AI — `claude` · `codex` · `gemini` — in the shell. **Assistants always launch in AUTO mode** (client `AI_CMD` map: `claude --permission-mode bypassPermissions` · `codex --dangerously-bypass-approvals-and-sandbox` · `gemini --yolo`) — the hidden flows fire `/… --approve` commands unattended, and a permission prompt mid-run would stall the job with nothing on screen. The server **augments PATH at startup** with the standard install dirs (`~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.npm-global/bin`; npm dir on Windows) because a double-clicked .app inherits launchd's minimal PATH — without this, installed assistants get greyed out in the pickers and `which()` misses them. The terminal drawer has an **End chat** button (shown once you start a Discussion) that sends the "done" signal to a running `/learn` discussion so it compacts and writes the chat. The AI launch buttons clear the input line first (Ctrl+U), so switching assistants never leaves leftover pre-typed text to delete by hand. The terminal drawer **never opens itself** — not on page load, not on navigation (an auto-reappearing drawer reads as a bug); it opens only on explicit action: the Terminal button, starting a Discussion, a "Show terminal" escape hatch, or End chat. A **discussion page** gets a **Remove discussion** button that calls `/api/remove-chat` to delete `chats/<slug>/` + its generated page and rebuild. Ghost-node and reading-queue Analyze/Dismiss/Keep actions live in `templates/graph_addon.html` (injected into `docs/graph.html` by the build); **Analyze opens the Analyze overlay with the id already in the bar** (`RR_openAnalyze`; `RR_openDiscuss` is the analogous hook) — never the terminal; dismissals persist to `dismissed.json`, which the build honors (ghosts have no *View PDF* — they aren't downloaded). Report pages get a *View PDF* button that opens the analyzed paper inside the app via the server's `/pdf` route (serves the local `papers/<id>.pdf` or proxies arXiv same-origin so it can be framed), and an **Edit notes** button — a full-screen editor for `reports/<id>/notes.md` backed by `GET/POST /api/notes` (id shape-validated against `reports/`; empty save deletes the file; save rebuilds + reloads). External links open in the system browser via `/api/open`. **Launching an AI always respawns the shared pty** (`respawn` ws message, epoch-guarded server-side) so `codex` is never typed into a running `claude`; the tutorial seen-flag is per-INSTALL: under work mode the key is `rr-tutorial-seen@wm:<install-id>` where the id is a random value persisted in `user/.install-id` on first server start (gitignored — so delete + re-clone into the SAME folder still counts as a fresh copy; a path hash did not); on file:///Pages it falls back to `rr-tutorial-seen@<site-root-path>`.

## Conventions
- Always pause at the command's **Gate** (outline / dimensions) before writing a digest or comparison — **unless `--approve` is passed** (still post the outline for the record, then write). `/refresh-venues` no longer gates (it applies only confident matches); `/remove` confirms the delete instead (skippable with `--approve`).
- Keep claims grounded; cite section/figure numbers; never invent metrics.
- To add a focus view, add it to `user/config.json` `sections` (or a `templates/fields/*.json` pack) and to the command's section list — it renders automatically wherever a digest provides it. **Don't edit `SECTION_ORDER` in `scripts/build.py`** — that's a fallback used only when no config declares sections, so edits there have no effect once a config exists. (Custom one-off sections — e.g. from `--focus` — render even without being listed.)
- **Field config & maintenance safety**: user-specific config (`profile.json`, `dismissed.json`, `config.json`) lives under **`user/`** (gitignored) so app updates never overwrite it; `scripts/build.py`'s `user_path()` resolves `user/<name>` → legacy repo-root `<name>` → shipped `*.example.json`, so an un-migrated repo still works. **Discipline is a config choice**: `user/config.json` names `fields` (e.g. `["ml"]`, `["bio"]`, `["econ-finance"]`) which merge the shipped `templates/fields/*.json` packs (tag vocabulary + focus-view titles + lens + tone), and may carry an explicit `tags`/`sections` override **alongside** `fields` — `merge_field_packs` is **base-wins**, so it keeps your explicit values and fills only what you omit (lens/tone) from the pack. **Merge order matters**: tags union in the order `fields` lists the packs, and each section key takes its title from the *first* pack that declares it, so `["bio","ml"]` ≠ `["ml","bio"]` — the primary field goes first. Packs are schema-checked at load (`PACK_KEYS`); a typo'd key warns instead of silently no-oping. `config.site_title` renames the whole site (header/titles/credit) without code edits. The shipped `ml` pack ships a **general, math-derived** default vocabulary; a reader's own specific vocabulary lives in their `user/config.json` `tags` (Setup can add custom focus views to `sections` too). The commands and `scripts/verify.py` read this at runtime — **do not hardcode ML**. `SECTION_ORDER`/`TAG_VOCABULARY`/`MAX_TAGS`/`REQUIRED_SECTIONS` in `scripts/build.py` are now defaults/fallbacks; the live values come from `load_config()` via `section_order()`/`tag_vocabulary()`/etc.
- **Never rename a section *key*** (`summary`/`math`/`architecture`/`results`/`significance`/`reproducibility`) — all existing digests use them as storage keys. Fields only change the *titles* (a pack titles `math` "Methods & statistics" for bio, etc.). Renaming a key blanks that tab on every existing report.
- **Citations**: digests carry `cites: [{id, title}]` (normalized arXiv ids). The graph links papers and surfaces a reading queue; edges resolve automatically as papers are added.
- **Tags**: a controlled vocabulary, broad (2–4 per paper), never paper-specific; `scripts/verify.py` fails on any tag outside the **active** set. The active set is `config.tags` (from the user's field pack(s) or override), with `scripts/build.py`'s `TAG_VOCABULARY` as the ML default. Add a category to the field config / pack deliberately rather than inventing a one-off tag.
- **`significance`** is a default, always-written section that merges novelty + critique + why-it-matters-for-the-field. `summary` + `significance` are required (build warns if missing). **`reproducibility` is opt-in**: `/explain-paper` writes it only when explicitly requested (`--views`/`--focus`) or when the reader's setup config includes it as a default view — never by default.
- **Deep dives**: a digest may carry a top-level `deepdives` array (`{title, added (ISO date), html}`); the build renders them under one "Deep dive" focus tab. Added incrementally by `/deep-dive` (append mode); `/deep-dive --into <key>` instead merges the worked content into an existing section's `html`. Not written by `/explain-paper`.
- **Discussions**: `/learn` compacts an interactive chat into a standalone `chats/<slug>/chat.json` (`{id, title, papers, added, tldr, html}`) — stored and surfaced **like a comparison**: its own `docs/chat/<slug>/` page, a "Discussions" list below the reading list, and a "Discussed in" backlink on each referenced report. It is **never** a digest or catalogue card. Same HTML/LaTeX/grounding rules as a digest section.
- **Reading state**: `status` (`to-read`/`reading`/`read`) + `priority` (0–3 stars) are seed values; the reader edits them in the UI (report page + Library page) and choices persist in `localStorage`, overriding the digest. New papers seed `to-read`/`0`. Per-paper prose lives in `reports/<id>/notes.md`. All browser reading state lives under `rr-*` keys (`rr-status-<id>`, `rr-prio-<id>`, `rr-tags-<id>`, `rr-dismissed`, `rr-theme`) — the avatar menu's **Back up** export/import and `isStateKey` cover exactly this set.
- **Custom tags / collections** (reference-manager-style): free-form, reader-owned labels (a project name, "to-cite", …), **distinct from the controlled `tags` vocabulary**. Stored per paper in `localStorage` (`rr-tags-<id>`, a JSON array), edited on the report page (a "Collections" chip editor) and the Library. On the **Library** they render as a collections filter bar + per-row chips + a "Tag selected papers" bulk action; filtering to a collection scopes the BibTeX **Copy/Download** to that set (the `.bib` is named after the collection). Nothing in `scripts/build.py` handles them — they're a pure client/localStorage feature (like reading state), so they're never in a digest and are carried by the reading-state backup.
- **Tutorial**: a bigger stepped walkthrough (`templates/account.html`, `.rr-modal-card--wide`). It **auto-opens on first launch** (one-shot `rr-tutorial-seen`) and on close hands off to **Setup**; it's re-openable anytime from the avatar menu ("Tutorial") and is skippable/closeable. Image steps show **real screenshots** (`assets/shots/*.png`, `{{ASSET_ROOT}}`-prefixed so they resolve at any page depth); the two GIF steps are still styled placeholders — record them once there's real usage to capture.
- **Example paper**: the template ships one digest — `reports/1706.03762/` (*Attention Is All You Need*) — so the first launch isn't empty, screenshots have content, and agents have a gold-standard reference for digest JSON/HTML/LaTeX conventions. Its PDF is **not** committed (`papers/*.pdf` stays gitignored); work mode's View PDF proxies arXiv. Users remove it with `/remove 1706.03762`.
- **Citations**: keep `source_url` on arXiv for the link, but set `published` (`{type: "article"|"inproceedings", venue, year, volume?, number?, pages?, publisher?}`) or a raw `bibtex` override so exported BibTeX is the journal/venue entry. `docs/library.html` is a grouped reference list with BibTeX export.
- Colors live in CSS tokens — `:root` is the default **light** theme, `[data-theme="dark"]` overrides. Every page has a persisted light/dark toggle. Don't hard-code colors; add a token.

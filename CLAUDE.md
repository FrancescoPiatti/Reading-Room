# Reading Room — Claude Code context

A personal catalogue of focused paper breakdowns. Reports are generated **interactively** (no Anthropic API, no `claude -p`) and rendered to a static site you can open locally or host on GitHub Pages.

## How it works
- `/explain-paper <arxiv-id | url | path.pdf> [--views …] [--depth …] [--audience …] [--focus "…"] [--approve]` reads a paper and writes `reports/<id>/digest.json` (structured data + per-section HTML you author). The input can be an arXiv id/URL, a direct PDF URL, or a **local PDF path** — that's how you add a paper that isn't on arXiv.
- `/compare <id> <id> [<id>] [--approve]` writes a side-by-side `compares/<slug>/compare.json`.
- `/learn <id> [topic] [--approve]` has an **interactive discussion** about a catalogued paper, then on **End chat** / "done" **compacts** it into a standalone Discussion stored like a comparison (`chats/<slug>/chat.json`) and listed **below the reading list** — it is never a paper/digest or catalogue card.
- `/deep-dive <id> <topic> [--into <section> | --append] [--approve]` authors a worked derivation / proof / mechanism trace and either **appends** it to the digest's `deepdives` array (a "Deep dive" tab) or **merges** it into a named section (asked per run).
- `/remove <id> [--approve]` deletes a paper (digest, notes, downloaded PDF, and the generated `docs/papers/<id>/` page) and rebuilds; it reports any comparisons / citations that referenced it. It is destructive, so it confirms the exact paths first unless `--approve` is given.
- `/refresh-venues` scans papers still marked as arXiv preprints, checks DBLP for a published version, and updates `venue` + `bibtex` for confident, non-CoRR matches while keeping the arXiv `source_url` (it applies them directly — no gate — relying on the conservative match test).
- `/backup export|import` packages **all on-disk user data** — `reports/` (analysed papers + notes), `compares/`, `chats/`, `user/` (profile/config/dismissals), and `papers/*.pdf` — into a single zip (`backups/reading-room-backup-<ts>.zip`), and restores it. It's a thin, safe wrapper around **`archive.py`** (pure stdlib): the generated `docs/` is excluded (rebuildable); `import` merges by default (`--replace` for an exact restore), first writes a safety snapshot to `backups/`, and refuses/skips unsafe zip entries (`..`, absolute paths, symlinks, out-of-scope files). Status/priority **stars** live in browser `localStorage`, so they're not in the zip: export/import those from the header **avatar menu → "Back up"** (a JSON, works on the static site too).
- `/setup` (replaces `/profile`) writes `user/profile.json` + `user/config.json` (who the reader is + their field/defaults) and **applies the customization directly, with minimal reader involvement** — it does **not** ask them to approve each change; the commands read the config at runtime so command-file edits are a genuine last resort (and, if ever needed, are applied without a per-edit gate and just mentioned in a single **final review** of how the setup looks). It personalizes the header and supplies defaults to the commands. The header **avatar menu** opens a **Profile** view (blurred-backdrop modal), an interactive **Setup** questionnaire, and a **Back up** dialog (export/import browser reading state as JSON); in work mode you launch an AI (Claude, Codex, or Gemini) on the final Setup step, then Finish posts the answers to the loopback server (`/api/setup-intake` → `.setup-intake.json`) and auto-runs `/setup` in that already-open terminal (it doesn't raise the drawer itself), where the agent confirms each change. On the static site Setup degrades to a copyable profile + instructions.
- `--approve` on `/explain-paper`, `/compare`, `/learn`, `/deep-dive` skips the Gate's wait (the outline is still posted for the record, then it writes straight away); on `/remove` it skips the delete-safety confirmation.
- `python build.py` (pure stdlib, no deps) renders every digest into `docs/papers/<id>/index.html`, rebuilds the searchable catalogue `docs/index.html`, the reference-library `docs/library.html`, the connections graph `docs/graph.html`, any comparison pages `docs/compare/<slug>/index.html`, and any discussion pages `docs/chat/<slug>/index.html`. It also copies the **self-hosted assets** into `docs/assets/`: vendored `fuse.min.js`/`d3.min.js` + the woff2 fonts from `templates/vendor/` (no Google Fonts / CDN pings; pages work offline — only MathJax stays on a pinned, SRI-checked CDN and degrades to raw LaTeX offline) and the tutorial screenshots from `assets/shots/`. `finalize_page` resolves two page-wide placeholders at the end: `{{SITE_TITLE}}` (config `site_title`, default "Reading Room") and `{{ASSET_ROOT}}` (`""` at docs root, `"../../"` for papers/compare/chat pages).
- `python verify.py --build` builds then runs QA (digest schema, **authored-HTML tag balance + LaTeX delimiter pairing**, **cites[].id normalization + `published` schema**, **field-pack validation**, placeholders, embedded-JSON, script balance, BibTeX, WCAG contrast). Prefer it over a bare build; the `verify-build` skill wraps it. Fix `✗` failures; `!` warnings are advisory.
- The source of truth is the digests in `reports/` (and `compares/`, `profile.json`). `docs/` is fully generated — never hand-edit it; re-run the build.
- Read PDFs with the Read tool directly (it renders pages). Don't leave extracted `.txt` next to PDFs — `papers/*.txt` and `.cache/` are gitignored.
- **Work mode (optional, local).** Double-click `ReadingRoom.app` (macOS) / `ReadingRoom.bat` (Windows), or `cd workmode && npm start`, to serve the same UI on `127.0.0.1` with an integrated AI terminal (Claude, Codex, or Gemini) + live rebuilds (it calls `python build.py`; it never reimplements the build). It is **purely additive** and loopback-only: the static `docs/` and the GitHub Pages browse path are untouched. Needs Node 18+ (static build still needs nothing but Python). The double-click launchers start the server headless (`ReadingRoom.app` opens no Terminal window at all and reports errors via a dialog; `ReadingRoom.bat` is the Windows launcher — logs go to `workmode/workmode.log`, pid to `workmode/workmode.pid`; closing the app window auto-quits the server); `npm start` instead runs it in the foreground with visible logs. **The .app must NOT detach the server** (`nohup …&` + exit): the server runs as the launcher's child with the launcher `wait`ing (LSUIElement keeps it out of the Dock) — a detached child dies when the app process exits. The .app also pre-flights **file access** (repo in a TCC-protected place — OneDrive/iCloud/Desktop/Documents — can be silently unreadable to the app even when Terminal reads it fine; cloud-evicted "dataless" files additionally hang `require()` at server start) and shows a grant-access dialog instead of failing silently. Both launchers make a one-shot first-run offer to add a Desktop shortcut (marker: `user/.desktop-shortcut-offered`; macOS = symlink, Windows = `.lnk` with `assets/ReadingRoom.ico`). The server falls back to the next port if one is busy (so a stale instance won't block a fresh launch). The bottom-drawer launcher is built from split buttons (a main action + a ▾ menu): a command picker (`/explain-paper` · `/compare` · `/learn` (discuss) · `/deep-dive`, pre-typed never auto-run; the ▾ switches which) and a Terminal button (main = toggle the drawer) whose ▾ launches an AI — `claude` · `codex` · `gemini` — in the shell. The terminal drawer has an **End chat** button (shown only once you start a `/learn` discussion from the picker) that sends the "done" signal to a running `/learn` discussion so it compacts and writes the chat. The command picker and the AI launch buttons clear the input line first (Ctrl+U), so switching between them never leaves leftover pre-typed text to delete by hand. Opening a paper **report auto-opens the terminal** (unless you've explicitly closed it before) so it's ready to discuss/deep-dive that paper; a **discussion page** gets a **Remove discussion** button that calls `/api/remove-chat` to delete `chats/<slug>/` + its generated page and rebuild. Ghost-node and reading-queue Analyze/Dismiss/Keep actions live in `templates/graph_addon.html` (injected into `docs/graph.html` by the build); dismissals persist to `dismissed.json`, which the build honors (ghosts have no *View PDF* — they aren't downloaded). Report pages get a *View PDF* button that opens the analyzed paper inside the app via the server's `/pdf` route (serves the local `papers/<id>.pdf` or proxies arXiv same-origin so it can be framed); external links open in the system browser via `/api/open`.

## Conventions
- Always pause at the command's **Gate** (outline / dimensions) before writing a digest or comparison — **unless `--approve` is passed** (still post the outline for the record, then write). `/refresh-venues` no longer gates (it applies only confident matches); `/remove` confirms the delete instead (skippable with `--approve`).
- Keep claims grounded; cite section/figure numbers; never invent metrics.
- To add a focus view, add it to `user/config.json` `sections` (or a `templates/fields/*.json` pack) and to the command's section list — it renders automatically wherever a digest provides it. **Don't edit `SECTION_ORDER` in `build.py`** — that's a fallback used only when no config declares sections, so edits there have no effect once a config exists. (Custom one-off sections — e.g. from `--focus` — render even without being listed.)
- **Field config & maintenance safety**: user-specific config (`profile.json`, `dismissed.json`, `config.json`) lives under **`user/`** (gitignored) so app updates never overwrite it; `build.py`'s `user_path()` resolves `user/<name>` → legacy repo-root `<name>` → shipped `*.example.json`, so an un-migrated repo still works. **Discipline is a config choice**: `user/config.json` names `fields` (e.g. `["ml"]`, `["bio"]`, `["econ-finance"]`) which merge the shipped `templates/fields/*.json` packs (tag vocabulary + focus-view titles + lens + tone), and may carry an explicit `tags`/`sections` override **alongside** `fields` — `merge_field_packs` is **base-wins**, so it keeps your explicit values and fills only what you omit (lens/tone) from the pack. **Merge order matters**: tags union in the order `fields` lists the packs, and each section key takes its title from the *first* pack that declares it, so `["bio","ml"]` ≠ `["ml","bio"]` — the primary field goes first. Packs are schema-checked at load (`PACK_KEYS`); a typo'd key warns instead of silently no-oping. `config.site_title` renames the whole site (header/titles/credit) without code edits. The shipped `ml` pack ships a **general, math-derived** default vocabulary; a reader's own specific vocabulary lives in their `user/config.json` `tags` (Setup can add custom focus views to `sections` too). The commands and `verify.py` read this at runtime — **do not hardcode ML**. `SECTION_ORDER`/`TAG_VOCABULARY`/`MAX_TAGS`/`REQUIRED_SECTIONS` in `build.py` are now defaults/fallbacks; the live values come from `load_config()` via `section_order()`/`tag_vocabulary()`/etc.
- **Never rename a section *key*** (`summary`/`math`/`architecture`/`results`/`significance`/`reproducibility`) — all existing digests use them as storage keys. Fields only change the *titles* (a pack titles `math` "Methods & statistics" for bio, etc.). Renaming a key blanks that tab on every existing report.
- **Citations**: digests carry `cites: [{id, title}]` (normalized arXiv ids). The graph links papers and surfaces a reading queue; edges resolve automatically as papers are added.
- **Tags**: a controlled vocabulary, broad (2–4 per paper), never paper-specific; `verify.py` fails on any tag outside the **active** set. The active set is `config.tags` (from the user's field pack(s) or override), with `build.py`'s `TAG_VOCABULARY` as the ML default. Add a category to the field config / pack deliberately rather than inventing a one-off tag.
- **`significance`** is a default, always-written section that merges novelty + critique + why-it-matters-for-the-field. `summary` + `significance` are required (build warns if missing).
- **Deep dives**: a digest may carry a top-level `deepdives` array (`{title, added (ISO date), html}`); the build renders them under one "Deep dive" focus tab. Added incrementally by `/deep-dive` (append mode); `/deep-dive --into <key>` instead merges the worked content into an existing section's `html`. Not written by `/explain-paper`.
- **Discussions**: `/learn` compacts an interactive chat into a standalone `chats/<slug>/chat.json` (`{id, title, papers, added, tldr, html}`) — stored and surfaced **like a comparison**: its own `docs/chat/<slug>/` page, a "Discussions" list below the reading list, and a "Discussed in" backlink on each referenced report. It is **never** a digest or catalogue card. Same HTML/LaTeX/grounding rules as a digest section.
- **Reading state**: `status` (`to-read`/`reading`/`read`) + `priority` (0–3 stars) are seed values; the reader edits them in the UI (report page + Library page) and choices persist in `localStorage`, overriding the digest. New papers seed `to-read`/`0`. Per-paper prose lives in `reports/<id>/notes.md`. All browser reading state lives under `rr-*` keys (`rr-status-<id>`, `rr-prio-<id>`, `rr-tags-<id>`, `rr-dismissed`, `rr-theme`) — the avatar menu's **Back up** export/import and `isStateKey` cover exactly this set.
- **Custom tags / collections** (reference-manager-style): free-form, reader-owned labels (a project name, "to-cite", …), **distinct from the controlled `tags` vocabulary**. Stored per paper in `localStorage` (`rr-tags-<id>`, a JSON array), edited on the report page (a "Collections" chip editor) and the Library. On the **Library** they render as a collections filter bar + per-row chips + a "Tag selected papers" bulk action; filtering to a collection scopes the BibTeX **Copy/Download** to that set (the `.bib` is named after the collection). Nothing in `build.py` handles them — they're a pure client/localStorage feature (like reading state), so they're never in a digest and are carried by the reading-state backup.
- **Tutorial**: a bigger stepped walkthrough (`templates/account.html`, `.rr-modal-card--wide`). It **auto-opens on first launch** (one-shot `rr-tutorial-seen`) and on close hands off to **Setup**; it's re-openable anytime from the avatar menu ("Tutorial") and is skippable/closeable. Image steps show **real screenshots** (`assets/shots/*.png`, `{{ASSET_ROOT}}`-prefixed so they resolve at any page depth); the two GIF steps are still styled placeholders — record them once there's real usage to capture.
- **Example paper**: the template ships one digest — `reports/1706.03762/` (*Attention Is All You Need*) — so the first launch isn't empty, screenshots have content, and agents have a gold-standard reference for digest JSON/HTML/LaTeX conventions. Its PDF is **not** committed (`papers/*.pdf` stays gitignored); work mode's View PDF proxies arXiv. Users remove it with `/remove 1706.03762`.
- **Citations**: keep `source_url` on arXiv for the link, but set `published` (`{type: "article"|"inproceedings", venue, year, volume?, number?, pages?, publisher?}`) or a raw `bibtex` override so exported BibTeX is the journal/venue entry. `docs/library.html` is a grouped reference list with BibTeX export.
- Colors live in CSS tokens — `:root` is the default **light** theme, `[data-theme="dark"]` overrides. Every page has a persisted light/dark toggle. Don't hard-code colors; add a token.
